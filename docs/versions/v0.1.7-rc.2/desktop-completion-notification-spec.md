# v0.1.7-rc.2 会话完成通知功能规格说明

> 状态：待实施，供其他 agent 执行
> 版本：v0.1.7-rc.2
> 功能目标：后台会话执行完成时及时提醒用户，并显示尚未查看的完成会话数
> 本文档范围：需求、行为、状态、架构边界、平台差异、测试和验收；不包含功能实现

## 1. 背景与目标

DeepSeek Harness Desktop 在用户关闭主窗口后可以继续在系统托盘中运行，dsh 会话也可以继续执行。用户可能在切换到其他应用或隐藏桌面窗口后，无法及时知道某个会话已经完成。

本功能在会话完成时提供两种互补的提醒：

1. 当主窗口不在前台时，显示操作系统原生通知，及时提醒用户后台会话已完成。
2. 在桌面应用的任务栏/应用图标上显示尚未查看的完成会话数量，用户稍后也能看到仍有完成结果待查看。

通知是纯提醒，不提供通知内回复或任务操作。

### 1.1 已确认的产品要求

| 项目 | 规则 |
|---|---|
| 待查看计数 | 统计用户尚未查看的已完成会话，不统计完成事件总次数 |
| 系统通知条件 | 仅当桌面主窗口不在前台时发送 |
| 通知用途 | 让用户及时得知后台执行的会话已完成 |
| 通知交互 | 只显示提醒，不提供回复、文本输入或操作按钮 |
| 多会话 | 每个尚未查看的完成会话计为 1，不因同一会话重复事件而重复计数 |

### 1.2 默认状态语义

以下细节是为使规格可实施而设定的默认规则；若实施时发现官方事件模型无法区分这些情况，必须先提交技术发现和影响，不得猜测或引入脆弱判断：

- 本次“完成”默认指正常完成的会话执行。运行中、等待审批、等待用户输入、已取消、启动失败或异常终止不计入成功完成数，也不触发本功能通知。
- 如果当前前台窗口正在显示刚刚完成的那个会话，则该完成结果视为已在用户正在查看的会话中呈现，不加入未读计数，也不发通知。
- 如果窗口虽然在前台，但用户当前正在查看其他会话，则完成会话仍计为未读；由于应用处于前台，不发系统通知。
- 用户在完成事件之后打开/切换到某个未读会话，该会话即视为已查看并从未读计数中移除。仅恢复窗口、切换到应用或点击托盘，不自动清除所有未读会话。
- 系统通知权限关闭或通知发送失败，不改变未读计数状态。

## 2. 现有架构与功能边界

### 2.1 已有托盘功能

同版本目录中已有托盘功能规格和实施验收记录：

- `docs/versions/v0.1.7-rc.2/desktop-tray-feature-plan.md`
- `docs/versions/v0.1.7-rc.2/desktop-tray-implementation-acceptance.md`

当前项目有两套桌面壳：

- Tauri 主桌面壳：Rust 主进程负责启动 dsh、管理 WebView、托盘和 child 生命周期。主要入口为 `tauri-app/src-tauri/src/main.rs`。
- Electron macOS 兼容壳：Electron 主进程负责启动 dsh、管理 BrowserWindow、Tray 和 child 生命周期。主要入口为 `electron-app/src/main.js`。

用户关闭主窗口会隐藏到托盘，托盘菜单显式退出时才退出应用。新功能不得改变这一生命周期，也不得因通知、徽标或状态持久化失败而关闭窗口、停止 dsh 或阻塞应用启动。

### 2.2 dsh 事件来源前置门槛

桌面壳加载的是随运行时提供的官方 `dsh web` UI。桌面端目前不能假定已经拥有“会话完成”或“用户已查看会话”的稳定原生事件接口。因此实施的第一步必须是事件发现，不是直接写 UI 监听代码。

实施 agent 必须先在项目当前锁定的官方 dsh runtime/UI、稳定 API 或既有客户端/host 事件中确认并记录：

1. 哪个稳定事件准确表示一次会话执行正常完成。
2. 该事件能否提供稳定的 session ID 和足以去重的完成周期/turn ID。
3. 哪个稳定事件能表示用户当前实际打开/正在查看的 session ID。
4. 两类信号在刷新、WebView 重载、会话切换、断线重连、事件重放和窗口隐藏时如何工作。
5. 完成、错误、取消、等待审批、等待用户输入等状态如何区分。

约束：

- 优先使用官方提供的稳定 API、事件总线、客户端状态接口或官方支持的扩展机制。
- 不得通过定时轮询 DOM、读取可见文案、匹配按钮文本、解析 window title 或解析日志来推断会话完成/已读。
- 不得修改、复制或 patch 官方 dsh 源码、前端 bundle 或打包 runtime 来制造事件。
- 若只能通过注入 WebView 脚本桥接既有的稳定应用事件，必须校验发送源、消息结构和 session ID，并遵守本规格第 7 节的安全边界。
- 如果找不到稳定且无侵入的事件来源，暂停后续实现，向项目负责人提交发现结果、不可行原因和备选方案；不得以 DOM 轮询或脆弱启发式替代。

## 3. 用户可见行为

### 3.1 主窗口在后台时完成

1. dsh 产生正常完成事件，桌面壳识别该 session 当前尚未查看。
2. 桌面壳持久化该 session 的未读状态并更新应用图标徽标。
3. 若主窗口当时不在前台，向操作系统请求显示一条原生通知。
4. 通知只说明有会话完成，不显示任务输入、回答正文、工具输出、凭据或敏感会话内容。
5. 用户稍后打开该会话后，该会话从未读计数中移除；徽标按剩余未读会话数量更新。

### 3.2 主窗口在前台时完成

- 不显示系统通知。
- 如果完成的 session 正是前台当前查看的 session，视为结果已经呈现，保持该 session 为已读状态，不增加徽标计数。
- 如果完成的 session 不是当前查看的 session，加入未读集合并更新徽标，但不弹系统通知。

### 3.3 窗口隐藏、最小化或失焦

以下状态统一视为“不在前台”，完成事件可触发系统通知：

- 窗口隐藏到系统托盘。
- 窗口最小化。
- 窗口仍可见但不拥有焦点。
- 用户当前正在使用其他应用。

前台判断必须从桌面壳/原生窗口状态读取，不以 WebView `document.visibilityState` 单独作为判断依据。

### 3.4 通知内容

通知使用平台原生通知样式，最小内容建议为：

- 标题：`DeepSeek Harness Desktop`
- 正文：`有会话已完成，等待查看。`

确切中英文文案可按当前应用语言本地化，但语义一致。默认不要显示 session 标题或对话内容，以免锁屏、共享屏幕或通知中心泄露用户信息。

通知不得包含：

- 回复输入框或 inline reply。
- “继续”“重试”“停止”等 action button。
- Prompt、模型回答、工具结果或 API Key。

点击通知的行为不在本功能承诺范围内。除非平台默认行为必然激活应用，否则不得附加自动导航、自动选择会话或清空未读状态。清除未读数的唯一业务条件是用户查看相应会话。

## 4. 未读会话计数与状态机

### 4.1 计数定义

徽标数字 = 当前未读集合中的不同 session 数量，而不是：

- 完成 turn 数。
- 通知发送次数。
- 历史上所有已完成会话的总数。

同一 session 在用户查看前再次产生重复/重放的完成事件，仍只计为一个未读会话。用户已查看后，该 session 在未来开启新一轮执行并再次完成，可再次成为一个未读会话。

### 4.2 状态转换

```text
RUNNING / WAITING / OTHER
  -- 官方正常完成事件 -->
      若 session 是当前前台正在查看的会话：READ（不加数、不发通知）
      否则：UNREAD（去重加入集合、徽标更新）
              若主窗口不在前台：尝试发送一次系统通知
              若主窗口在前台：不发送系统通知

UNREAD
  -- 用户打开/切换到该 session --> READ（从集合移除、徽标更新）
  -- 同 session 重复完成事件 --> UNREAD（不重复计数、不重复通知）
  -- 应用退出/重启 --> UNREAD（从本地状态恢复）

READ
  -- 新的独立完成周期 --> 按当前前台查看状态重新判定
```

如果官方信号能准确区分不同的完成周期，去重键应同时包含 session ID 和完成周期/turn ID。未查看状态仍按 session 去重。若官方信号没有完成周期 ID，使用可证明稳定的事件 ID 或等价序列号；不得用墙上时钟单独充当唯一键。

### 4.3 通知节流与重复控制

- 一条新未读记录最多触发一次通知请求。
- 同一 session 的重复事件、WebView 刷新重放、应用重连重放不能重复弹通知。
- 不同 session 在短时间内完成时，每个 session 都应进入未读集合；实现可使用操作系统原生通知合并/替换策略，但不能丢失未读数。
- 通知被系统折叠、勿扰模式抑制或用户关闭，不得回滚未读记录。
- 通知失败只记不含敏感数据的诊断日志，不重试到形成通知风暴。若需要重试，应有明确次数/去重规则，默认不做后台无限重试。

### 4.4 已读判定

- 主窗口恢复、获得焦点、关闭通知气泡、点击系统通知、回到应用首页，都不自动清空全部未读会话。
- 用户将具体未读 session 打开并使其成为主界面当前查看会话后，才清除该 session 的未读状态。
- 用户正在查看某会话期间，该会话正常完成时按第 3.2 节判定为已读。
- 批量清空所有未读、全部标记已读等功能不在范围内。
- 如果官方 UI 没有稳定的“当前查看 session”信号，不得用 DOM 文本推断；按第 2.2 节暂停并报告。

## 5. 状态持久化与恢复

### 5.1 存储边界

未读状态跨应用关闭/重启保留，避免用户错过后台完成后徽标消失。数据只能存入桌面应用专属本地数据目录：

- Tauri 使用当前平台对应的 app data/local data 路径。
- Electron 使用 Electron `app.getPath('userData')` 或该壳既有的专用状态目录。

不得写入或更改 `~/.dsh` 会话数据库、dsh 配置、官方 runtime 或工作区文件。

两套壳各自存储时，至少保证同一已安装应用实例/发行渠道的未读状态跨该应用重启保留；Tauri 与 Electron 两个不同发行版之间不要求共享未读数据库。实现结果需记录实际路径和权限。

### 5.2 记录结构

实现可选用 JSON、SQLite 或项目已有的本地存储方式，优先最小依赖，并至少保存：

- schema version。
- 稳定 session ID。
- 完成事件/完成周期去重标识。
- 首次完成时间。
- 未读/已读状态，或仅保存当前未读集合并在查看时删除。
- 已读时间（若选择保留历史读状态）。

不保存 session 正文、提示词、回答文本、API 凭据或 URL token。

### 5.3 原子性和恢复

- 完成事件处理要保证“去重记录 + 未读状态更新 + 徽标刷新”不会因重复事件造成多计数。
- 状态文件应使用原子替换或数据库事务，避免应用强制退出留下半写文件。
- 文件缺失表示没有待查看状态，正常启动且徽标归零。
- 状态数据损坏、未知 schema 或写入失败时：不得阻断应用启动；记录安全诊断日志，恢复为可用空状态或保留可恢复备份；不能误报旧徽标数字。
- 应用启动时读取未读集合，并立即把徽标恢复为其 distinct session 数量。
- 显式退出和窗口隐藏不清除未读集合。

## 6. 桌面壳事件流

### 6.1 逻辑数据流

```text
官方 dsh 稳定会话事件
        |
        v
受校验的桌面事件桥接
        |
        +--> 去重与未读集合持久化
        |        |
        |        +--> 更新系统应用图标徽标
        |
        +--> 检查主窗口是否前台
                 |
                 +--> 后台：请求原生系统通知
                 +--> 前台：不请求系统通知

用户切换/打开 session
        |
        v
清除该 session 未读状态 --> 持久化 --> 更新徽标
```

状态更新应先保证持久化结果一致，再以最佳努力更新平台徽标/发通知。一个平台 API 失败不得使另一种提醒状态丢失。

### 6.2 Tauri 主壳

实现者需在 `tauri-app/src-tauri/src/main.rs` 或职责清晰的新 Rust 模块内处理：

- 调用已确认的 session complete/session viewed 桥接入口。
- 校验 payload 并执行去重、持久化和未读计数更新。
- 通过原生通知能力请求 Windows/Linux/macOS 系统通知（以实际发布平台和依赖能力为准）。
- 更新 Windows 任务栏应用按钮徽标；确认所用 API 操作的是窗口/taskbar app identity，而不是系统托盘溢出区图标。
- 更新其他桌面平台上有明确定义的应用徽标。
- 查询主 `WebviewWindow` 是否 visible/focused，以判断是否发送 toast。
- 处理通知权限/API 不可用、窗口未创建、app 正在退出等情况。

必须保留已实现托盘功能的 `quitting` 状态、`request_quit`、child 回收和单实例恢复行为。事件或通知不得在 Rust 主线程上执行长时间 I/O；并发/异步处理应避免锁住现有 child 状态。

### 6.3 Electron 兼容壳

实现者需在 `electron-app/src/main.js` 或新主进程模块内处理：

- 使用 Electron 原生 `Notification` 或经验证的 Windows 原生通知机制。
- Windows 上使用支持 BrowserWindow/taskbar 的 overlay/icon badge API 显示未读数，不要把计数只画在 Tray 图标上。
- macOS 上使用通知中心和 Dock badge；徽标更新时不激活 Dock 或抢焦点。
- 从 Electron 主窗口查询 `isFocused()`、`isVisible()`、`isMinimized()`，依第 3.3 节前台定义决定通知。
- 恢复本地未读状态后立刻同步 badge；用户查看具体 session 后清理并同步 badge。
- 保留已实现的托盘菜单、窗口隐藏、显式退出、`before-quit`、单实例和 child 生命周期行为。

Electron 兼容壳不得因完成通知切换成独立进程或新窗口；应用图标通知状态由当前主进程统一管理。

## 7. 安全、权限与隐私

- 通知由桌面主进程创建和展示，WebView 不得直接调用任意原生通知/图标 API。
- WebView 到主进程的事件必须限制到可信本地 dsh 主页面/主 frame；拒绝未知 sender、子 frame、任意 URL 或未经 schema 校验的事件。
- 对 session ID、事件 ID 长度和字符集做校验；不得将事件 payload 直接拼入 shell、路径、菜单或日志。
- 日志只记录事件类别、脱敏后的稳定 ID 摘要、处理结果和错误类型，不记录对话内容、token、cookie、密钥或完整 URL。
- 通知使用通用文案，默认不显示会话标题/内容。
- 系统关闭通知权限时，桌面应用不应反复弹权限请求或循环重试；未读徽标仍保持正确。
- 只增加实现当前平台 API 必需的最小通知/图标依赖或配置，并解释每项变更；不能为此整体升级 Tauri/Electron 或扩大 WebView 权限。

## 8. 变更范围

允许按技术发现最小化修改：

- `tauri-app/src-tauri/src/main.rs` 或新增的 Tauri 原生通知/状态模块。
- `electron-app/src/main.js` 或新增的 Electron 主进程通知/状态模块。
- 若事件桥接确有必要，添加受校验的桌面桥接代码；不得修改官方 dsh 源码/runtime。
- Tauri Cargo manifest/lock、Electron 打包配置或图标资源仅在原生通知/徽标 API 确实要求时修改。
- 与状态逻辑、事件契约和平台呈现相关的测试及验收记录。

禁止修改：

- dsh 官方源码、官方 Web UI bundle 和 `tauri-app/resources/runtime/` 中的运行时。
- `~/.dsh`、会话文件、用户凭据和工作区文件。
- 已实现托盘的关闭/退出/child 回收语义。
- 无关版本号、NSIS 安装逻辑、发布流程和其他不相关 UI。

如实现者认为只有修改官方 runtime 才能获得可靠事件，应停下报告，不得违反上述边界自行 patch。

## 9. 平台行为矩阵

| 平台/桌面壳 | 原生通知 | 图标未读数 | 要求 |
|---|---|---|---|
| Windows / Tauri | Windows 系统通知 | Windows taskbar 应用按钮 overlay/角标 | 必须真实验收；证明更新的是 taskbar button 而非 tray overflow icon |
| Windows / Electron 开发或目标壳 | Windows 系统通知 | BrowserWindow/taskbar overlay/角标 | 若用于发行或行为回归，按 Windows 实测并记录 Electron API 限制 |
| macOS / Electron 兼容壳 | macOS Notification Center | Dock badge | 与 Windows 的未读语义一致；不因 badge 更新抢前台 |
| macOS / Tauri（若发行） | macOS 原生通知 | Dock/app badge（按 Tauri API 可用性） | 明确验证；不可把托盘菜单栏图标当作 Dock 徽标 |
| Linux / Tauri（若发行） | 当前桌面环境原生通知 | 仅在桌面 shell 提供稳定机制时 | 通知必测；徽标缺乏通用 API 时记录“不支持/环境限制”，不伪称等价 |

平台能力差异不改变“未读按 session 去重、查看 session 后清除、只有窗口后台才发通知”的产品语义。

## 10. 测试与验收矩阵

### 10.1 状态与去重单元测试

- 首个 session 完成事件：未读集合含该 session，计数为 1。
- 同一完成事件 ID 重放：计数保持 1。
- 同一 session 的同一完成周期不同传输重放：仍只计 1。
- 不同 session 完成：distinct 未读 session 数按 1、2、3 增加。
- 用户查看其中一个 session：只移除该 session，其他未读项保留。
- 已读 session 开始新完成周期并再次完成：再次加入未读集合。
- 取消、失败、等待审批、等待输入和仍运行状态：默认不进入未读集合。
- 当前前台正在查看的 session 完成：按第 1.2 节视为已读。
- 当前前台查看另一个 session 时完成：增加未读数但不发 toast。

### 10.2 前台判定和通知集成测试

分别验证窗口：

- visible + focused。
- visible + unfocused。
- minimized。
- hidden to tray。
- 尚未创建或正在退出。

完成事件到来时，只有 visible + focused 才属于前台；其余状态均按后台通知。前台不发送系统通知，但未读徽标仍依据具体 session 是否已查看而更新。

通知集成检查：

- 后台新未读 session 触发一次原生通知。
- 重复事件不再重复通知。
- 前台事件不触发通知。
- 系统通知禁用/权限拒绝/发送异常不影响未读集合及徽标。
- 通知不含回复输入、action button、Prompt、回答正文或敏感会话标题。

### 10.3 持久化与徽标测试

- 关闭再启动后恢复全部未读 session 和正确徽标。
- 查看一个 session 并重启后，该 session 保持已读，其余未读项恢复。
- 未读数为 0 时清除系统徽标/overlay。
- 同一 session 重复记录不会增加 badge 数。
- 状态文件缺失、截断、schema 版本未知、读取失败和写入失败时应用仍可启动并记录不含敏感内容的错误。
- 应用退出与完成事件同时发生时不得写入重复记录或留下部分状态。

### 10.4 真实平台验收

Windows Tauri 真实运行/安装包必须检查：

1. 隐藏到托盘后继续执行一条可控会话。
2. 会话完成时 Windows 右下角出现系统通知。
3. 任务栏应用按钮（不是托盘溢出区图标）显示未读数字。
4. 在前台完成当前查看会话不出现通知且不增加未读数。
5. 前台查看其他会话时不弹通知，但正确更新未读数字。
6. 点击打开已完成会话后数字正确递减，全部查看后消失。
7. 重启应用后未读状态和徽标恢复。

Electron/macOS 兼容版须验证 Notification Center 和 Dock badge。Linux 若仍是发行目标，至少在指定发行桌面环境验证原生通知并记录徽标能力。

### 10.5 回归验收

确认新增功能不改变：

- 关闭窗口隐藏到托盘行为。
- 托盘打开主界面和退出行为。
- 单实例恢复与聚焦。
- dsh child 启动、正常退出、异常退出和清理。
- 会话数据仍与官方 dsh CLI 按既有规则互通。
- WebSocket、窗口下载接管、cookie/token 脱敏和代理抗性。

静态检查、单元测试或模拟通知不能代替 Windows 真实 toast/taskbar 角标和 macOS Notification Center/Dock badge 的平台验收。

## 11. 完成定义

只有全部满足以下条件才能标记完成：

1. 已找到并记录稳定、无官方源码改动的会话完成事件与会话查看事件。
2. 未读状态按 distinct session 去重，重复/乱序事件不会多计或误清。
3. 未读状态保存在桌面应用本地数据中，跨重启恢复，不污染 `~/.dsh`。
4. 主窗口在前台时不发系统通知；后台/托盘隐藏/最小化/失焦时的新未读完成 session 发一次通知。
5. 通知仅为提醒，没有 inline reply 或操作按钮，不泄露敏感内容。
6. taskbar/app badge 显示尚未查看的完成会话数量，打开具体会话后准确递减，全部查看后清零。
7. 系统通知权限关闭或原生 API 失败时，未读状态仍正确且应用不崩溃。
8. Tauri/Windows 和 Electron/macOS 的实际平台行为符合矩阵，支持范围和无法实现的 badge 限制有据可查。
9. 现有托盘、单实例、child 生命周期、会话与下载功能回归通过。
10. 交付包括变更清单、事件来源证据、依赖/权限说明、平台测试环境和逐项验收结果。

## 12. 推荐实施顺序

1. 事件发现：确认官方 dsh runtime 中正常完成、完成周期 ID 和当前查看 session 的稳定信号；提交简短技术发现记录。若事件不稳定或只能靠 DOM/日志推断，暂停并回报。
2. 独立状态逻辑：实现 session 去重、未读集合、已读清除和跨重启持久化，并以单元测试覆盖重复/乱序/并发事件。
3. Tauri Windows：接入原生通知、前台判定和 Windows taskbar application button 数字徽标；先完成真实运行验收。
4. Electron/macOS：接入 Notification Center 和 Dock badge，复用相同产品语义和状态测试。
5. 其他已发布平台：按平台矩阵验证，不支持的徽标如实标记，不改变未读状态逻辑。
6. 完成真实平台测试、回归测试并补充实施验收记录。

实现者不得在通知/徽标验收通过前扩展到通知设置页、会话通知历史、任务操作按钮或对话内回复等范围外功能。
